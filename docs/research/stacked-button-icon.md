# How `cs-button` shows an icon above its label

**Status:** research only. Nothing implemented. Resolves the research half of
[#174](https://github.com/CruGlobal/cornerstone-design-system/issues/174).
**Date:** 2026-10-09
**Repo state read:** `origin/main` at `8a301fb`. Repo paths below are relative to the repo root.
**Related:** [#173](https://github.com/CruGlobal/cornerstone-design-system/issues/173) (avatar as a dropdown
trigger), [#217](https://github.com/CruGlobal/cornerstone-design-system/issues/217) (icon-button check and
`cs-badge`), [#182](https://github.com/CruGlobal/cornerstone-design-system/issues/182) (component property naming).

---

## Short answer

Add an `orientation` attribute to `cs-button` (`horizontal` | `vertical`, default `horizontal`). In `vertical`
the button lays its existing slots out in a column: `start` above the label, `end` (and the caret) below it.
The vertical layout drops the fixed height for a minimum height, and it does not apply to an icon-only button.
Expose content alignment separately, as one component property, `--cs-button-justify-content`, read with a
`center` fallback. Both are additions with unchanged defaults, so neither blocks 1.0.0.

The rest of this file is the evidence.

---

## 1. What `cs-button` does today

- **Three slots in one row.** The rendered `<button>` or `<a>` holds `start`, the default (label) slot and `end`,
  in that DOM order, then the caret and the spinner
  (`packages/components/src/components/button/button.ts:314-322`). The JSDoc lists the same three slots
  (`button.ts:32-34`) and parts `button`, `start`, `label`, `end`, `caret`, `spinner` (`button.ts:36-41`).
- **The row is a centred flex row of fixed height.** `.button` is `display: inline-flex`,
  `align-items: center`, `justify-content: center`, `height: var(--cs-form-control-height)`, `width: 100%`
  (`packages/components/src/components/button/button.styles.ts:23-54`, `justify-content` at line 26,
  `height` at line 41).
- **The fixed height is built from tokens that a stacked layout can reuse.**
  `--cs-form-control-height` is `round(2 * --cs-form-control-padding-block + 1em * --cs-form-control-value-line-height, 1px)`,
  with `padding-block: 0.75em` and `padding-inline: 1em`
  (`packages/components/src/styles/themes/cru.css:384-389`, same in `default.css:375-382`).
  `cru.css` is generated by Sarah's `tools/palette.mjs` (`cru.css:1`), so any new token goes through her.
- **Spacing between slot content and the label is a slotted margin, and it is `!important`.**
  `slot[name='start']::slotted(*) { margin-inline-end: 0.75em !important }`, and the same on `end` and the caret
  with `margin-inline-start` (`button.styles.ts:357-366`). The `!important` defends against page-level margin
  resets (`packages/components/src/components/callout/callout.styles.ts:55-72`). Cornerstone uses this CSS
  approach instead of upstream's `HasSlotController` with `with-start` / `with-end` attributes, which the
  fork point still had
  ([upstream `button.ts` at the fork point, lines 60 and 88-98](https://github.com/shoelace-style/webawesome/blob/63f2b66ddc48f0d66574d2e9c2076dbf60fb8fb5/packages/webawesome/src/components/button/button.ts)).
  The contributing guide names this exact rule as the "reach for CSS first" example
  (`packages/docs/src/content/docs/resources/contributing.md:454-472`).
- **The icon-button state reads only the default slot.** `handleLabelSlotChange()` sets `isIconButton` when the
  default slot holds a `cs-icon` and no text and no other element, then sets the `icon-button` custom state
  (`button.ts:198-239`). Icon buttons get a square box: `width: var(--cs-form-control-height); aspect-ratio: 1`
  (`button.styles.ts:243-254`).
- **`size` sets one `font-size` on the host** (`packages/components/src/styles/component/size.styles.ts:4-22`);
  everything inside the button is `em`, except radius (`--cs-border-radius-*`, rem) and border width.
- **Line height is inherited, not set.** No rule in `button.styles.ts` sets `line-height`. Upstream removed it
  on purpose ([webawesome#2366](https://github.com/shoelace-style/webawesome/pull/2366)). On a page using
  Cornerstone's native styles the body line height is `--cs-line-height-normal`, `1.6`
  (`packages/components/src/styles/native.css:24-34`, `cru.css:268`). Today that does not change a button's
  height, because the height is fixed. It will once a stacked layout drops the fixed height (section 7).
- **`cs-button` is `@status stable`** (`button.ts:22`). Adding a property or a custom property to a stable
  component is a `minor` change; removing or renaming one is `major` (`docs/standards/api-surface.md:22-23`).

## 2. What Flightdeck had to do

The Flightdeck port built a labelled icon rail out of `cs-button`s (commit `7db1983a` on the branch
`cornerstone-port` in the local checkout `~/CruGlobal/flightdeck-cornerstone-port`; not on any remote as of
this writing, so push it if someone else needs to read it). Paths in this section are in that checkout.

- It did **not** use the `start` slot. It put a `<span class="cs-stack">` holding the `cs-icon` and a `<small>`
  label inside the default slot (`app/views/shared/_icon_rail.html.erb:46-49`).
- It restyled the button part for two lines: `height: auto`, `padding-block: var(--cs-space-xs)`,
  `padding-inline: var(--cs-space-2xs)`, `border-radius: var(--cs-border-radius-m)`
  (`app/assets/stylesheets/cornerstone/page.css:12-21`). The radius line restates the default
  (`--cs-form-control-border-radius` is `--cs-border-radius-m` in both shipped themes, `cru.css:362`,
  `default.css:353`), so the real fixes were height and padding.
- It set `style="width: 100%"` on each button so the rail's buttons share one width, and
  `aria-current="page"` on the host of the current section (`_icon_rail.html.erb:42-45`).
- It rendered two forms, a column on desktop and a row in the mobile drawer, switched by `cs-page`'s view
  (`_icon_rail.html.erb:14-18`). Both forms are stacked buttons.

**Why the default slot and not `start`:** a consumer cannot move a `start` icon into a column from outside. The
`0.75em !important` inline margin on slotted `start` content (`button.styles.ts:359-361`) wins over any page
rule, even an `!important` one, because "for important rules the declaration from the inner context wins"
([CSS Cascade 5, Context](https://www.w3.org/TR/css-cascade-5/#cascade-context)). In a column with
`align-items: center` that margin pushes the icon `0.375em` off centre. So a CSS-only recipe has to abandon the
`start` slot.

## 3. Cornerstone conventions that bear on the choice

- **`orientation` is an established attribute name.** Nine components declare
  `orientation: 'horizontal' | 'vertical'`, eight of them reflected (`carousel` is the one that is not):
  `split-panel.ts:60`, `slider.ts:183`, `carousel.ts:87`, `divider.ts:25`, `radio-group.ts:78`,
  `checkbox-group.ts:51`, `scroller.ts:36`, `button-group.ts:35`, `card.ts:83-84` (all under
  `packages/components/src/components/`).
- **`cs-card` is the closest precedent.** Its `media` slot is documented as rendering "at the start of the
  card" (`card.ts:20`). In the default `vertical` orientation it renders first, above the header
  (`card.ts:107-109`); in `horizontal` it renders to the left of the body (`card.ts:94-101`,
  `card.styles.ts:118-131`). So Cornerstone already has a slot whose "start" means "top" when the orientation
  is vertical.
- **CSS itself calls the top "start" in a column.** In `flex-direction: column`, "the main-start and main-end
  directions are equivalent to the block-start and block-end directions"
  ([CSS Flexbox 1, flex-direction](https://www.w3.org/TR/css-flexbox-1/#flex-direction-property)). In a
  horizontal writing mode, block-start is the top. That answers the ticket's worry that "start" reading as
  "top" is unclear: it is the same reading CSS logical properties already use.
- **Booleans default to `false`, and `with-*` / `without-*` are for showing or hiding content**
  (`contributing.md:189-194`). A `vertical` boolean would be legal but would be the only boolean spelling of an
  axis in a library that spells it `orientation` nine times.
- **Properties change behaviour, custom properties change appearance, and "will this need to change based on
  screen size?" favours a custom property** (`contributing.md:307-311`). This argues for alignment as a custom
  property (section 6), and it is the strongest argument against `orientation` as an attribute (see
  Rejected options).
- **Use a part to let one element take styles; use a custom property for a value reused or set from outside**
  (`contributing.md:313-321`).
- **Focus and reading order follow the flattened tree; no focusable element is moved with `order`,
  `row-reverse` or grid placement** (`packages/docs/src/content/docs/resources/accessibility.md:64-67`,
  `docs/standards/accessibility.md:42-43`).
- **Component property naming, from #182:** `--cs-<component>-<property>`, read with a fallback, nothing set on
  `:host`, each default written once
  ([#182 resolution comment](https://github.com/CruGlobal/cornerstone-design-system/issues/182)). The glossary
  term is "component property" (PR #228, open).

> [!WARNING]
> **Conflict in the standards.** The canonical contributing guide still says the opposite of #182: "scope them
> to the `:host` block" and "Do not use the `--cs-` prefix, as that is reserved for design tokens"
> (`contributing.md:277-301`, lines 281 and 290). `docs/standards/api-surface.md` does not yet carry the #182
> rule (#182 says it will, under UIUX-197), and no component uses the new naming yet
> (`grep -rn "@cssproperty \[--cs-" packages/components/src/components` finds nothing). This file follows #182
> as the task directs. The guide needs the UIUX-197 rewrite before anyone builds from it.

## 4. Web Awesome upstream

- **Upstream has no stacked layout and no alignment API.** The fork point and the current `next` head have the
  same three slots and the same centred, fixed-height row
  ([fork point `63f2b66`](https://github.com/shoelace-style/webawesome/blob/63f2b66ddc48f0d66574d2e9c2076dbf60fb8fb5/packages/webawesome/src/components/button/button.ts),
  [`next` at `e99dc5e`](https://github.com/shoelace-style/webawesome/blob/e99dc5e26ae63410bd481aa8a686a61ff7158ccd/packages/webawesome/src/components/button/button.ts)).
  The upstream Button docs page has no stacked example
  ([`button.md` on `next`](https://github.com/shoelace-style/webawesome/blob/next/packages/webawesome/docs/docs/components/button.md)).
  Searching upstream issues for stacked, vertical or icon-above buttons found nothing.
- **Upstream has been asked for content alignment.**
  [webawesome#1527](https://github.com/shoelace-style/webawesome/issues/1527) asked for a way to set label
  alignment in a vertical button group. One upstream contributor wanted to make it "more easily configurable,
  either via attribute or CSS custom property", and an upstream member replied "+1 for making it easy to
  configure". It was closed as fixed by centring everything, with no setting added.
- **One upstream fix since the fork matters here.**
  [webawesome#2694](https://github.com/shoelace-style/webawesome/pull/2694) (merged 2026-08-14, after the
  2026-08-11 fork point recorded in `packages/components/NOTICE`) found that `visibility: hidden` on a loading
  button's content "removes the content from the accessibility tree, so the button could end up with no
  accessible name". It switched to `opacity: 0` and added `aria-busy`. Cornerstone still uses
  `visibility: hidden` (`button.styles.ts:312-321`) and sets no `aria-busy` (`button.ts:288-313`). This is a
  bug in every button, not only stacked ones, so it belongs in its own ticket (see Facts later tickets depend on).

separate `top` slot. Two put the setting on a dedicated navigation or toolbar item rather than on the general
button (Fluent, Ionic); Cornerstone has no tab-bar or toolbar-button component, and Flightdeck reached for
`cs-button`. Only Primer exposes content alignment, and it does so as a separate setting from its visuals.

## 6. The shapes, weighed

### A `top` slot

- No surveyed system does this (section 5).
- It is meaningful in one layout only, and it leaves `top` + `start` + `end` undefined together.
- Material switches the icon between top and start by screen width (section 5). With a slot, that means moving
  the icon element between slots; with an attribute, it is one attribute change.
- A matching `bottom` slot built with `column-reverse` would break the focus and reading order rule
  (section 3). Built in DOM order it is fine, but it is a fourth slot.

### An `orientation` attribute (recommended)

- Matches nine existing `orientation` properties and the `cs-card` `media` precedent (section 3), and the
  CSS model where block-start is the top.
- Matches the surveyed systems: one icon, one layout setting (section 5).
- Touches no slot and reads no slot content, so it needs no `HasSlotController`, no `with-*` SSR attribute,
  and no change to the icon-button detection. It renders the same on the server, because it is an attribute
  selector.
- The ticket's catch, that `end` sits below the label, is the logical result, and it gives the caret a place
  (below the label) in a stacked dropdown trigger. Whether the caret should sit there is a design call
  (Open design questions).
- Cost: switching by screen width needs the app to change the attribute. `cs-page` already gives apps a
  `view` attribute (`'mobile' | 'desktop'`, `packages/components/src/components/page/page.ts:218`), and
  Flightdeck already renders per view.

### A CSS recipe only

- Works today only by abandoning the `start` slot (section 2), so the recipe would teach a different
  structure from the documented one ("Start & End Decorations",
  `packages/docs/src/content/docs/components/button.md:156-178`).
- Needs three overrides (column stack in the label, `height: auto`, padding) that every app repeats, and
  Flightdeck shows they get it slightly wrong (a restated radius, per-button `width: 100%`).
- Leaves the label's height to the page's line height (section 1).

## 7. Interactions

**`size`.** All new values must be `em` so `size` keeps working through one `font-size`
(`size.styles.ts:4-22`). With the sketch values in the Recommendation (padding-block
`--cs-form-control-padding-block` 0.75em, a 1em icon, a 0.25em gap, a 1.2em label line), a stacked button is
about 3.95em tall: about 47px at `xs` (12px), 55px at `s`, 63px at `m`, 79px at `l`, 99px at `xl`
(font sizes from `cru.css:243-247`). At `m` that is close to Material's 64dp bar. Radius stays rem, so the
corners read tighter on large stacked buttons.

**Fixed height.** In `vertical`, replace `height: var(--cs-form-control-height)` with `height: auto` and
`min-height: var(--cs-form-control-height)` (Primer's `labelWrap` does the same, section 5). Also set the
label's `line-height` to `var(--cs-form-control-value-line-height)`, which eight form controls already do
(`input.styles.ts:28`, `select.styles.ts:74`, `checkbox.styles.ts:12` and others under
`packages/components/src/components/`). Without it the stacked height changes with the page's line height
(1.6 under native styles versus the 1.2 the control height assumes, `cru.css:267-268`).

**Margins.** The `!important` inline margins on slotted `start`, `end` and the caret
(`button.styles.ts:359-366`) must become block margins in `vertical`, also `!important`, or the icon sits
`0.375em` off centre (section 2). These margins are load-bearing: they are the only thing collapsing an empty
slot.

**`pill`.** `pill` sets every corner to `--cs-border-radius-pill`, `9999px` (`button.styles.ts:257-262`,
`cru.css:307`). On a tall stacked box that draws a capsule. Leave `pill` as it is and say so in the docs;
Flightdeck chose the default radius for its two-line buttons (`page.css:12-15`).

**`with-caret`.** The caret renders after `end` and hides `end` when present (`button.ts:317-321`,
`button.styles.ts:293-306`). In `vertical` it falls below the label, and its `margin-inline-start: 0.75em`
(`button.styles.ts:363-366`) must flip like `end`'s.

**`loading`.** The spinner is absolutely centred with `top: calc(50% - 0.5em); left: calc(50% - 0.5em)`
(`button.styles.ts:323-333`), which works for any box shape, and `visibility: hidden` keeps the box's size.
The accessible-name problem from webawesome#2694 (section 4) applies to stacked buttons the same as any other.

**The `icon-button` state, and #173 and #217.**

- A stacked button has text in its default slot, so it is never an icon button. Nothing in `orientation`
  reads the default slot.
- An icon-only button with `orientation="vertical"` has nothing to stack. The vertical rules should exclude it
  (`:host([orientation='vertical']) .button:not(.is-icon-button)`), so the square shape wins.
- **Constraint on #173 and #217:** keep `isIconButton` and the `icon-button` state the single source of
  "this button is icon-only". If #173 widens detection to a lone `cs-avatar`, or adds an explicit opt-in, it
  should set that same state, and the vertical rules and the alignment rule (section 9) will exclude it with
  no further change. A second flag would need both rules updated.
- **Constraint on #173 and #217:** keep detection reading only the default slot. If detection started
  counting `start` or `end`, a stacked button (icon in `start`, text in the label) would still have text, so
  it is safe, but the rules would no longer be independent.
- **Reverse constraint:** the stacked layout requires the icon in `start`. An icon placed in the default slot
  beside text is not stacked. Docs must say so.
- **Badges (#217):** a badge pins to the host's top-end corner from any slot (`button.styles.ts:5-20, 340-351`,
  and `button.md:141-154`). On a wide stacked button (a full-width rail item), that corner is far from the
  icon. Material and most bottom navs badge the icon, not the item. Whether a stacked button's badge should
  pin to the `start` container is a design question; it does not change #217's question.

**Other attributes.** `constructLightDOMButton()` copies every host attribute onto a temporary native button
for form submission (`button.ts:141-150`), so `orientation` is copied too. That is harmless (an unknown
attribute on a native button) but worth a line in the PR. `orientation` must not set `aria-orientation`:
ARIA 1.2 allows it only on `scrollbar`, `select`, `separator`, `slider`, `tablist`, `toolbar` and roles that
inherit from them ([WAI-ARIA 1.2, aria-orientation](https://www.w3.org/TR/wai-aria-1.2/#aria-orientation)),
and `button` is not one.

## 8. Inside `cs-button-group`

- The group's flex container is its `<slot class="button-group">`: `display: flex`, `flex-wrap: wrap` by
  default, `row` or `column` by the group's `orientation`
  (`packages/components/src/components/button-group/button-group.styles.ts:8-38`). The slotted `cs-button`
  hosts are its flex items, so they stretch on the cross axis.
- Corner radii and border overlap come from private `--_button-*` variables keyed to the **group's**
  orientation (`button-group.styles.ts:40-92`, read at `button.styles.ts:48-51, 78-79`). They do not depend on
  the button's own layout, so a stacked button joins the group's corners correctly.
- **Vertical group of stacked buttons:** the hosts stretch to one width and `.button` is `width: 100%`
  (`button.styles.ts:42`), so a column of stacked buttons gets equal widths with no per-button
  `width: 100%`.
- **Horizontal group of stacked buttons:** the hosts stretch to the tallest, but each `.button` is only as
  tall as its own content. Equal content gives equal heights. To be safe, the vertical layout could use
  `height: 100%` instead of `auto`: the Flexbox spec treats a stretched item's cross size as definite ("the
  cross sizes of items in auto-sized flex containers are also considered definite",
  [CSS Flexbox 1, 9.8](https://www.w3.org/TR/css-flexbox-1/#definite-sizes)), and outside a stretching parent
  `100%` behaves as `auto`. This is reasoning from the spec, not a measurement; the PR should test it in all
  three engines.
- **Mixed group (stacked beside one-row buttons):** the one-row buttons keep their fixed height inside
  stretched hosts, so the group's heights do not match. Changing the one-row height would touch the
  `--cs-form-control-height` alignment every form row relies on, so do not. Document "do not mix
  orientations in one group" instead.
- Found along the way: `findButton()` matches `cs-radio-button`, which does not exist in this library
  (`button-group.ts:81-86`; `ls packages/components/src/components` has no `radio-button`), and the group sets
  `aria-orientation` on a `role="group"` element and on its own host (`button-group.ts:37-43, 69-71`), which
  ARIA 1.2 does not list for `group`. Neither affects this ticket.

## 9. Content alignment

- Today the only way is `cs-button::part(button) { justify-content: start }`, which works because `button` is a
  documented part (`button.ts:36`). The Button page already teaches part overrides for one-off restyles
  (`button.md:232-236`).
- **Recommended: one component property, `--cs-button-justify-content`,** read as
  `justify-content: var(--cs-button-justify-content, center)` on `.button`. Reasons:
  - Alignment is appearance and often changes by screen width (full width and start-aligned on a phone, centred
    on a desktop), which the guide says favours a custom property (`contributing.md:307-311`).
  - A custom property can be set once on a section, such as a sidebar, and reaches every button in it,
    including buttons inside other components' shadow roots. That is #182's stated reason for the naming
    ("A value can be set on the page, a theme class, a section, or one element").
  - Upstream was asked for this, and its maintainers agreed it should be easy to configure (section 4).
    Primer ships it (section 5).
  - It is one value feeding one CSS property, so naming it after that property (like
    `--cs-carousel-aspect-ratio` in #182) tells a CSS author the allowed values.
- **Not on the same API as `orientation`.** Orientation changes several declarations at once and is
  structural; alignment is one value a section sets. Primer keeps them apart too.
- **Scope it.** Apply it only to `.button:not(.is-icon-button)` in the horizontal layout. An icon button's
  content is wider than its square's content box (a 1.25em icon in a 2.7em box with 1em padding each side), so
  `start` would shift the icon. A stacked button should always centre, as every surveyed system does.
- **What it does not solve:** a menu-style row where the label sits at the start and a trailing icon or caret
  sits at the far end. `start` keeps `end` beside the label. Primer solves this with a separate
  `trailingAction` locked to the end (section 5). In Cornerstone a one-line recipe covers it:
  `cs-button::part(end) { margin-inline-start: auto }` (the `end` container is a flex item,
  `button.styles.ts:268-274`). Whether that deserves its own API is an open design question.

## 10. Accessibility: what the code already settles

These are established from code. None of them was checked with a screen reader.

- **The label stays the accessible name.** `orientation` changes layout only; the DOM order (`start`, label,
  `end`) is unchanged (`button.ts:314-316`). A `cs-icon` with no `label` sets `aria-hidden="true"`, and one
  with a `label` becomes `role="img"` with that `aria-label` (`packages/components/src/components/icon/icon.ts:270-282`).
  So a decorative `start` icon adds nothing to the name, and a labelled one adds its label before the text.
- **Visual order matches DOM order.** A column puts `start` above the label and `end` below it with no `order`
  or `column-reverse`, so the order rule holds (`accessibility.md:64-67`). Slotted content in `cs-button` is not
  focusable anyway; the native `<button>` or `<a>` is the one focus stop (`button.ts:50`, `delegatesFocus`).
- **The focus ring follows the box.** It is `outline: var(--cs-focus-ring)` with
  `outline-offset: var(--cs-focus-ring-offset)` (1px) on `.button` (`button.styles.ts:221-224`, `cru.css:315-316`),
  so it traces whatever shape the stacked box takes.
- **Target size.** With the sketch values, a stacked button is at least `--cs-form-control-height` tall
  (32px at `xs`) and at least 3.25em wide (1.25em icon canvas, `icon.styles.ts:16-23`, plus 1em padding each
  side: 39px at `xs`). That clears 2.5.8's 24 by 24 CSS px at every size
  ([Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). Flightdeck's
  tighter override (`padding-inline: 4px`) leaves a two-letter "AI" tile near 28px wide, still above 24.
- **`aria-current` is not forwarded.** Flightdeck sets `aria-current="page"` on the `cs-button` host
  (`_icon_rail.html.erb:45`). `cs-button` renders no `aria-current` on its inner `<a>` (`button.ts:288-313`),
  while `cs-pagination` renders it inside its own shadow root (`pagination.ts:364, 378`). Whether the host
  attribute reaches assistive technology is unverified; it is a question below.
- **Loading drops the name.** See section 4 and webawesome#2694.

## Open design questions

These need a designer, and the Figma component is a human job. Figma was not checked for this research.

1. The gap between icon and label in `vertical` (sketched as `0.25em`; Material uses 4dp at a 24dp icon,
   Flightdeck used `--cs-gap-3xs`, 2px).
2. Vertical padding: reuse `--cs-form-control-padding-block` (0.75em) or something tighter (Flightdeck used
   8px, Material 6dp). Inline padding: keep `--cs-form-control-padding-inline` (1em) or tighten for rails.
3. Whether `vertical` enlarges the `start` icon. Fluent sets it to 24px, Material uses 24dp beside a 12sp
   label; Cornerstone's icon is 1em by default.
4. Where the caret goes in `vertical`: below the label (what `orientation` gives for free) or beside it.
5. Where a badge pins on a stacked button: the button's corner (today) or the icon.
6. Whether a menu-style row (label at start, trailing item at the far end) earns its own API.

## Recommendation

**Add `orientation` to `cs-button`, and add one component property for content alignment.**

```ts
/** Lays out the button's content in a row, or stacks the `start` slot above the label and `end` below it. */
@property({ reflect: true }) orientation: 'horizontal' | 'vertical' = 'horizontal';
```

```text
@cssproperty [--cs-button-justify-content=center] - How a one-row button aligns its content along the row.
  Ignored by icon-only and vertical buttons.
```

Shape of the styles (values marked "design" wait on the questions above):

```css
.button:not(.is-icon-button) {
  justify-content: var(--cs-button-justify-content, center);
}

:host([orientation='vertical']) .button:not(.is-icon-button) {
  flex-direction: column;
  justify-content: center;
  height: 100%; /* or auto; test in a stretched group (section 8) */
  min-height: var(--cs-form-control-height);
  padding-block: var(--cs-form-control-padding-block); /* design */
  line-height: var(--cs-form-control-value-line-height);
}

:host([orientation='vertical']) slot[name='start']::slotted(*) {
  margin-inline-end: 0 !important;
  margin-block-end: 0.25em !important; /* design */
}

:host([orientation='vertical']) slot[name='end']::slotted(*),
:host([orientation='vertical']) [part='caret'] {
  margin-inline-start: 0 !important;
  margin-block-start: 0.25em !important; /* design */
}
```

- **Rule order.** The vertical margin rules have the same specificity as the caret's existing rule, so they go
  after the slot margin rules at `button.styles.ts:357-366`.
- **Additive.** Both default to today's behaviour, so this is a `minor` change on a stable component with an
  `Added:` changeset (`api-surface.md:22-23`). It can land before or after 1.0.0.
- **No new slot, part, state or token.** No `with-*` SSR attribute is needed, because nothing reads slot
  content.
- **Docs (Anna):** a "Stacked" example on the Button page that puts the icon in `start`, notes that `pill`
  draws a capsule, says not to mix orientations in a group, and shows the alignment property with the
  `::part(end)` recipe.
- **Tests:** vertical layout in client and hydrated fixtures; icon-only button ignores `vertical`; alignment
  ignored by icon-only buttons; a horizontal group of stacked buttons has equal heights in all three engines.
- **Separate tickets:** the loading accessible-name bug (Facts below).

## Rejected options

- **A `top` slot (and `bottom`).** No surveyed system does it; it is meaningful in one layout; it leaves
  `top` with `start` and `end` undefined; switching by screen width means moving elements between slots; and
  a `bottom` built with `column-reverse` breaks the order rule. (Sections 5, 6.)
- **A CSS recipe only.** A consumer cannot move a `start` icon into a column, because the slotted
  `!important` margin wins over any page rule, so the recipe must drop the `start` slot. It also repeats three
  overrides in every app and leaves height to the page's line height. (Sections 2, 6.)
- **A boolean `vertical` (Fluent's shape).** Legal under the boolean rule, but the library spells the axis
  `orientation` nine times. (Section 3.)
- **An `icon-position` or `layout` enum (Material's and Ionic's shape).** Names the icon, but `start` holds any
  element, not only icons, and enumerating positions grows the way Ionic's six values did, including an
  `icon-bottom` that needs `column-reverse`. `orientation` covers top and start with the existing slots.
  (Section 5.)
- **Orientation as a component property** (for example `--cs-button-orientation`, read with a container style
  query). It would switch by screen width with no script, which the guide favours. Rejected for now: stacking
  changes several declarations, which a custom property can only toggle through `@container style(...)`; the
  library has no style query today (`grep -rn "@container" packages/components/src` finds one size query, in
  `known-date.styles.ts:104`); and caniuse lists Chrome's and Edge's support as partial
  ([caniuse, style queries](https://caniuse.com/css-container-queries-style)). Worth revisiting as a
  cross-cutting policy, not for one component.
- **Alignment as an attribute (Primer's shape).** Discoverable and typed, but cannot respond to media queries
  and cannot be set once for a section. (Section 9.)
- **Alignment on the `orientation` API.** Different kinds of change; no surveyed system combines them.
  (Section 9.)
- **Only documenting the `::part(button)` override for alignment.** It works, and remains the fallback if the
  property is declined, but it cannot be set for a section of buttons in other shadow roots, and upstream
  users have asked for a named setting. (Section 9.)

## Open questions for the accessibility reviewer

1. **Name with a labelled start icon.** When a stacked button's `start` icon has a `label`, the name becomes
   "icon label + text" (section 10). Should the docs require the `start` icon to be decorative when a visible
   label is present, and should the button warn when it is not, the way it warns for an unlabelled icon button
   (`button.ts:233-238`)?
2. **Focus ring in a tight row.** Bottom bars often place items with no gap (Material's `ItemBetweenSpace` is
   0dp, `NavigationBarTokens.kt:48-49`). With a 1px outward offset, adjacent stacked buttons' rings can overlap
   or be clipped by a container. Should a stacked button inset its ring, or should the docs require a minimum
   gap?
3. **Target size floor.** The default metrics clear 24 by 24 at every size (section 10). Is AA's 2.5.8 the
   right floor for a stacked navigation item, or should `vertical` carry a larger minimum (2.5.5's 44px,
   Material's 48dp)? Should it set a `min-inline-size` so a short label like "AI" does not make a narrow tile?
4. **Current-page state.** Should `cs-button` forward `aria-current` from its host to the inner `<a>`, the way
   `cs-dropdown` writes ARIA onto the inner button (`dropdown.ts:751-765`) and `cs-pagination` renders it
   itself? And is a change from `appearance="plain"` to `"filled"` an acceptable non-colour signal for the
   current item (1.4.1), including under forced colours, where background fills are dropped?
5. **Navigation semantics.** Material and Ionic make these items tabs (`role="tab"` with selected state).
   For a web navigation bar of links, should Cornerstone's docs prescribe `<nav>` + links +
   `aria-current="page"` and rule out tab roles?
6. **Small labels and zoom.** Stacked labels tend to be small (Flightdeck uses 11px, `cs-font-size-2xs`;
   Material 12sp) and the button is `white-space: nowrap` (`button.styles.ts:30`). At 200% zoom (1.4.4) or with
   text spacing overrides (1.4.12), a fixed-width rail can clip them. Should stacked labels be allowed to wrap,
   and is there a minimum label size?
7. **Loading.** Confirm the loading bug (section 4) is a finding, and whether upstream's fix
   (`opacity: 0` plus `aria-busy`) is the one to adopt.
8. **Side finding.** `cs-button-group` sets `aria-orientation` on `role="group"` and on its host
   (`button-group.ts:37-43, 69-71`), which ARIA 1.2 does not list for `group`. Is that a finding? Not verified
   against axe.

## Facts later tickets depend on

- **The recommendation is additive.** `orientation` defaults to `horizontal` and the alignment property
  falls back to `center`, today's value (`button.styles.ts:26`). `minor`, `Added:`. Not a 1.0.0 blocker.
- **The icon-button state is the one switch.** Both the vertical layout and the alignment property exclude
  `.is-icon-button`. #173 and #217 should keep that state as the only "icon-only" signal and keep detection
  reading only the default slot (section 7).
- **The stacked layout needs the icon in `start`.** Default-slot content is never stacked.
- **A consumer cannot remove the `start` slot's margin.** It is `!important` inside the shadow root, and the
  inner `!important` wins ([CSS Cascade 5](https://www.w3.org/TR/css-cascade-5/#cascade-context)). Any future
  layout change to slotted spacing must be made inside the component.
- **Load-bearing values touched:** `--cs-form-control-height` (one-row height and the stacked minimum),
  `--cs-form-control-padding-block` (used inside that height and proposed for stacked padding),
  `--cs-form-control-value-line-height` (the 1.2 the height assumes), and the `0.75em` slotted margins
  (`button.styles.ts:359-366`). The one-row button's fixed height must not change; it keeps buttons level with
  inputs.
- **No new token is needed.** Every proposed value is an existing `--cs-*` token or an `em` literal. If the
  design answers call for a new token, that goes to Sarah.
- **Loading bug, own ticket:** `cs-button` hides its content with `visibility: hidden` while loading
  (`button.styles.ts:312-321`) and sets no `aria-busy`, which can leave it with no accessible name. Upstream
  fixed this after the fork in [webawesome#2694](https://github.com/shoelace-style/webawesome/pull/2694). A
  behaviour fix: `patch`, `Fixed:`.
- **Standards conflict, own ticket or UIUX-197:** `contributing.md:277-301` contradicts #182 on where custom
  properties are set and whether they use `--cs-`. Anyone implementing `--cs-button-justify-content` should
  follow #182.
- **Stale selector:** `button-group.ts:82` matches `cs-radio-button`, which does not exist.
- **Docs inconsistency for the accessibility owner:** `resources/browser-support.md` says "We specifically test
  with these screen reader and browser combinations", while `resources/accessibility.md:10-14` says it "does
  not claim a screen reader was run".
